### H1. Пополнение цели — гонка read-modify-write ✅
**`src/services/goalService.ts:84-103`**


Читает → считает в JS → пишет. Два одновременных пополнения (двойной клик, две вкладки) читают одно и то же значение и записывают одно и то же — **одно пополнение теряется**. При этом `DataContext.tsx:160` создаёт расход на **каждое** из них.

### H14. Импорт: одна плохая запись убивает всю коллекцию, и это молча ✅
**`src/services/dataService.ts:18-26, 100-113`**

Три дефекта работают в связке:

```ts
const asNumber = (value: unknown): number => {
  const n = Number(value);
  return Number.isFinite(n) ? n : 0;      // ← мусор превращается в 0
};
const asDateKey = (value: unknown): string =>
  /^\d{4}-\d{2}-\d{2}$/.test(text) ? text : ...;   // ← пропускает 2026-02-30 и 2026-13-45
```
```ts
const { error } = await supabase!.from(table).insert(values);   // ← один батч на всё
if (error) { console.error(...); if (!failuresAllowed) throw error; return; }  // ← проглатывается
```

1. `asNumber` отдаёт `0` для любого мусора, а в БД стоит `CHECK (amount > 0)`.

**Как чинить:** валидировать каждую строку до вставки, битые отбрасывать со счётчиком, вставлять пачками с `returning: 'minimal'` и показывать пользователю «импортировано 499 из 500, 1 пропущена».

## 3. MEDIUM — неверно в краевых случаях или заметно мешает

### M1. `asDateKey` подставляет UTC-день вместо локального ✅
**`src/services/dataService.ts:25`** — `new Date().toISOString().slice(0, 10)`.

Это **прямое нарушение правила, записанного в самом проекте**. `formatters.ts:48-51` предупреждает: «`toISOString()` must never be used to derive one: east of UTC it returns the previous day during the early morning». Ташкент — UTC+5: импорт между 00:00 и 05:00 проставит битым датам **вчерашний** день.
**Чинить:** использовать `toDateKey()` из `formatters.ts`.

### M2. `budgetService` мутирует экспортируемую константу — «Сброс данных» в демо не работает ✅
**`src/services/budgetService.ts:46-51`**, **`src/services/mockData.ts:404-410, 455`**

`getBudgets()` при пустом хранилище возвращает **сам объект** `INITIAL_BUDGETS`, а не копию. Строка 50 (`current[existingIndex] = updatedItem`) правит его на месте. `resetToDefaults()` потом пишет в localStorage уже испорченную константу — сброс не возвращает исходные лимиты.
**Чинить:** во всех геттерах `mockData` возвращать копию (`[...INITIAL_BUDGETS]`).

### M3. `updateProfile` вставляет строку профиля без `email`, а колонка `NOT NULL` ✅
**`src/services/profileService.ts:78`** против **`001_initial_schema.sql:8`**

`upsert({ id, ...updates, updated_at })` при сохранении, скажем, только валюты формирует INSERT без `email`. Postgres проверяет `NOT NULL` на предлагаемом кортеже **до** разрешения конфликта, поэтому если строки профиля нет — сохранение настроек падает с сырой ошибкой БД.
**Чинить:** всегда включать `email` в payload, либо перейти на явный `update` с фолбэком на `insert`.

### M4. Импорт бюджетов падает целиком при двух записях одной категории ✅
**`src/services/dataService.ts:119-125`** — `upsert` с `onConflict: 'user_id,category'`. Если в файле две записи по одной категории, Postgres отвечает `ON CONFLICT DO UPDATE command cannot affect row a second time` и **весь блок бюджетов** не импортируется.
**Чинить:** дедуплицировать по категории до отправки.
